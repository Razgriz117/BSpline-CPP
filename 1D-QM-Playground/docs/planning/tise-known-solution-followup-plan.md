# TISE known-solution verification: bug-fix + hardening plan

> Companion doc to `tise-release-readiness-plan.md`, same convention: plan first, "Implementation status (post-execution)" appended once the work lands.

## Context

The prior release-readiness pass (`docs/planning/tise-release-readiness-plan.md`, Parts A-G, committed at `8236239`) unified `solveTISE`/`tise_solver`'s grid+drop-set construction and wired several diagnostics, on the strength of tests that mostly check plumbing (finite values, state counts, warning-text substrings). Independently of this conversation, two rounds of rigorous physics verification were produced under `docs/tests/reports/` — one directory per solver commit (`9d0f04b`, `8236239`) — each comparing the real `tise_solver` binary's output against independently-computed analytic/numeric references (closed-form formulas, `mpmath.coulombf` Coulomb functions, `scipy.optimize.brentq` root-finding, Richardson-extrapolated finite-difference eigenvalues) for all 7 `tests/*.yaml` known-solution configs, via `verify_known_solutions.py`/`verify_new_tests.py`.

The user asked to examine these results and determine what (if anything) needs to change to fix bugs / meet requirements, and to keep a persistent plan+debrief document, matching this project's established convention.

**Headline finding**: 6 of 7 configs pass cleanly. **`interior_singularity` FAILS by 41%** — a genuine, diagnosed, demonstrated-fixable bug in the A4b "singular-join B-spline removal" feature the release-readiness pass shipped. Several other real (lower-severity) defects were also found. Per the user's explicit scope decision, this plan fixes all of them, not just the critical bug.

## Part A: Fix interior singular-join B-spline removal (closes H1)

Root cause (`TISE/tise.cpp`): `strategicKnotsFromJoins` (`:988-1006`) gives `Singular` joins `extra = 0` — no extra knot multiplicity — so an interior singular point is just an ordinary simple grid node. `buildStrategicGridAndDropSet` (`:1173-1217`) then calls `bSplinesTouchingX` at that point and drops the *entire cluster* (~`order` B-splines) whose support merely touches it, which is far more aggressive than a true point-Dirichlet condition and creates the dead zone documented in `interior_singularity.md` §2/§4.

Fix, per `interior_singularity.md` §5/§7 item 1 (already demonstrated numerically to $10^{-11}$–$10^{-15}$ against all 12 exact eigenvalues using `scipy.interpolate.BSpline`):
- For a `Singular` join **not** coincident with `rMin`/`rMax`, give it knot multiplicity $k-1$ (i.e. `extraMultiplicity = order - 2`, one more than `Step`'s `order - 3`) instead of 0. `strategicKnotsFromJoins` doesn't currently see `rMin`/`rMax`; thread that through (or filter the joins list at the `buildStrategicGridAndDropSet` call site before it's passed in) so edge-Singular joins are untouched — they're already correctly regularized by `BSpline::init`'s own clamping and the existing `atLeftEdge`/`atRightEdge` `continue` at `:1209-1210`.
- Replace the interior-Singular branch's `fillDropSet` contribution: instead of the full `bSplinesTouchingX` cluster, identify the *single* B-spline that is actually non-zero at $x_s$ on the new degenerate-knot grid (candidate shortlist from `bSplinesTouchingX` on the updated grid, numerically filtered via `bs.eval(x_s, e_i, ...)` for a unit vector `e_i` per candidate, keeping only the non-zero one — mirrors how edges already resolve to a single `B_1`/`B_N`).
- Both `solveTISE` and `tise_solver_main.cpp` inherit the fix automatically (both go through `buildStrategicGridAndDropSet`).

Tests: strengthen `TISE/tests/test_tise.cpp`'s `BuildStrategicGridAndDropSetTest.InteriorSingularityTriggersBSplineRemoval` / `SolveTISETest.InteriorSingularityTriggersBSplineRemoval` and `tests/test_analysis_integration.py:612-644`'s `TestInteriorSingularityRealSubprocess` with tight eigenvalue assertions from `interior_singularity.md` §7 item 3 ($E_1\approx\pi^2/800$ to $10^{-9}$, $E_3\approx0.1005405216$ to $10^{-8}$) — these fail hard against the current 41%-off code, confirming the tests actually discriminate before trusting them green.

## Part B: Fix $d\delta/dE$ and $\delta$ storage/plotting (closes H2, H3)

Per the user's chosen approach: internal fine local grid + branch unwrapping (lower risk than re-deriving an analytic derivative; avoids the `MatchAsymptoticDDeltaDESignTest`-style approach's dependence on a coincidentally-smooth production grid).

- In `matchAsymptotic`, for each requested energy, evaluate the raw $\mathrm{atan}$-based $\delta$ at a small internal step (e.g. $\Delta E\sim10^{-3}$, or scaled relative to the existing `poleTolFraction`-based pole-avoidance distance) on either side of the requested energy, track continuity across that fine window (add/subtract $\pi$ whenever consecutive raw values jump by more than $\sim\pi/2$ — a resonance/branch-jump signature), and central-difference the unwrapped $\delta$ directly.
- Remove the $\sin2\delta/\cos2\delta$ chain-rule inversion entirely — it's not just a discretization artifact, it's an inherent 0/0 conditioning problem at $\delta\approx\pi/4\ (\mathrm{mod}\ \pi/2)$ that shrinking the step cannot fix.
- Apply the same continuous-unwrapping logic across the full production energy grid for `result.delta` itself (not just the fine sub-window), so `phase_shifts.dat`/`phase_shifts.png` store/plot a physically legible, continuous $\delta(E)$ instead of raw $\mathrm{atan}(\cdot)-kR$ — closes H3. `analysis.py`'s existing `plot_phase_shifts` needs no change once the underlying data is sane; verify the plot is no longer "uninformative" per the free_particle/finite_square_well reports.

Tests: add a dedicated `matchAsymptotic` unit test comparing the new $d\delta/dE$ against the closed-form derivative of $\delta(E)=\arctan(\frac{k}{K}\tan Ka)-ka$ for finite_square_well at the energies `verify_new_tests.py` already evaluated ($\delta=1.464,-0.131,-1.253,-1.939,-2.074$ at $E=0.1..0.5$); keep `MatchAsymptoticDDeltaDESignTest` (still a valid sanity check) alongside it. Tighten `tests/test_analysis_integration.py`'s `TestFiniteSquareWellRealSubprocess.test_phase_shift_matches_analytic_square_well_formula` tolerance from `5e-2` to something matching the now-demonstrated $2.4\times10^{-4}$ rad accuracy, and add a $d\delta/dE$ assertion there and to `TestHydrogenConfigFileRealSubprocess` (currently has none).

## Part C: Gate Case-3 taper on `continuum.enabled` (closes H4)

In `tise_solver_main.cpp`, only pass `case3RightR`/`case3RightDelta` into `fillBandedMatrices` when `tise.continuum.enabled` is true; otherwise integrate the raw (untapered) potential to the wall, per `case3_irregular_tail.md` §7 item 1. Update `FillBandedMatricesCase3WindowTest`/`TestCase3RemediationRealSubprocess` to check both branches — continuum enabled: taper active (existing behavior); continuum disabled: taper inactive, bound eigenvalues matching the untapered reference (`verify_new_tests.py`'s $E^{\rm raw}$ column) to $\sim10^{-8}$.

## Part D: Refuse continuum construction on right-edge-singular potentials (closes H5)

In `tise_solver_main.cpp`, when `sgr.rightEdgeSingular` and `tise.continuum.enabled` are both true, skip `buildContinuumState`/`matchAsymptotic`/`writeContinuumInfo` entirely — write no `phase_shifts.dat`/`continuum_state_NNN.dat` — and emit a `warnings.json` entry explaining continuum output was skipped and why (a config error is not appropriate here since the bound-state solve is still fully valid and useful). Update `TestRightEdgeSingularWarningRealSubprocess`: keep the warning-text assertion, add assertions that the continuum output files do not exist. Unaffected: hydrogen (left-edge singular) and generic Case-3/Irregular tails (a different, non-singular condition).

## Part E: Strengthen physics regression coverage (closes H8)

For each affected e2e test class in `tests/test_analysis_integration.py` — `TestFiniteSquareWellRealSubprocess`, `TestHydrogenConfigFileRealSubprocess`, `TestCase3RemediationRealSubprocess`, `TestRightEdgeSingularWarningRealSubprocess`, `TestInteriorSingularityRealSubprocess` (free_particle/harmonic_oscillator's existing coverage is already tight per both reports' PASS verdicts — no change needed there) — add or tighten numeric assertions sourced directly from the relevant `docs/tests/reports/8236239/*.md` report and its companion `verify_known_solutions.py`/`verify_new_tests.py` (reference values already independently computed and vetted; no new physics derivation needed here, just wiring the existing numbers into `pytest.approx` assertions with the tolerances the reports demonstrate). ## Implementation status (post-execution)

All of Parts A-E landed, fully as scoped ("fix everything found"). Final regression state: all 4 C++ suites green (`ctest --test-dir TISE/build`; `TISETests` now carries 167 cases, up from 165), and all 193 Python tests green (`pytest tests/`, up from 185). Net diff for this phase: 5 files changed, 479 insertions, 117 deletions. Every fix was independently cross-checked against the actual numeric reference values in `docs/tests/reports/8236239/*.md` (and, for Parts A/C, by re-running the reports' own `verify_new_tests.py` against the fixed binary — see below) rather than trusting the new unit/integration tests alone.

**Part A — interior singular-join B-spline removal: fully fixed.** `buildStrategicGridAndDropSet` now gives an interior `Singular` join knot multiplicity `order-1` and drops only the single B-spline numerically non-zero there (found via `bs.eval` probing the `bSplinesTouchingX` candidate shortlist), instead of dropping the whole touching cluster on a simple-knot grid. Verified three ways: (1) new C++ tests `BuildStrategicGridAndDropSetTest.InteriorSingularityUsesKnotMultiplicityNotClusterRemoval` and `SolveTISETest.InteriorSingularityEigenvaluesMatchExactSplitDomainSpectrum` match the exact split-domain spectrum to 1e-9/1e-8; (2) the real-subprocess `TestInteriorSingularityRealSubprocess` tests confirm the same through `tise_solver_main.cpp` (`nEnBound` now exactly 50, was 36; eigenvalues match to the same tolerances); (3) re-running `docs/tests/reports/8236239/verify_new_tests.py` against the fixed binary shows the solver's own eigenvalues agree with both the exact reference and the script's independent `scipy.interpolate.BSpline`-based "proper" reconstruction to ~1e-11–1e-13 across all 12 states — the same standard the original report used to diagnose the 41% bug, now met.

**Part B — $d\delta/dE$ and $\delta$ storage: fully fixed, with one deviation found during implementation.** `matchAsymptotic` now takes `order`/`Hmat`/`Smat` so it can internally call `precomputeBoundaryCoupling` and evaluate raw $\delta$ at a small fine step ($\pm10^{-3}$, clamped to keep $E-h>0$) around each requested energy, central-differencing the unwrapped result instead of finite-differencing $\sin2\delta$ across the production grid. The $\sin2\delta/\cos2\delta$ inversion is gone entirely.
*Deviation from plan*: the plan's H3 fix (continuously unwrapping the stored production-grid $\delta(E)$ itself) initially used the obvious "snap to the branch closest to the previous point" heuristic — this **failed** against the real `finite_square_well.yaml` (δ jumped to 3.011 instead of the correct −0.131 at E=0.2, an exact-one-π mispick), because δ genuinely changes by more than $\pi/2$ between production grid points for this potential (confirmed: $d\delta/dE\approx-19$ at $\Delta E=0.1$ is an actual ~1.9 rad change), which a "closest raw value" heuristic cannot distinguish from an atan branch artifact. Fixed by using the already-computed, grid-spacing-independent fine-step $d\delta/dE$ to Euler-extrapolate a *predicted* next value and snapping to the branch closest to *that* instead — this was caught by directly running the real `finite_square_well.yaml`/`hydrogen.yaml` configs through the fixed binary and comparing against the reports' own tables, not by an automated test (none of the new C++/Python tests used a grid coarse enough to expose it). After the fix, both configs' $\delta(E)$ values match the reports' tables to 4+ decimal places (mod $\pi$), and `phase_shifts.png` now shows the expected smooth trajectory (visually confirmed via a full `controller.py` run) instead of the old "uninformative" $-45$ to $-100$ raw-atan plot.

**Part C — gate Case-3 taper on `continuum.enabled`: fully fixed.** `tise_solver_main.cpp` now only sets `case3RightR`/`case3RightDelta` when continuum is enabled; the warning message is worded differently for each branch. Verified against `case3_irregular_tail.yaml` (which has continuum disabled) both via a new test asserting the ground state now matches the untapered reference (`0.0092368363`, report §4 $E^{\rm raw}$ column) to `1e-7`, and independently via `verify_new_tests.py`: the re-run shows the solver's eigenvalue (`0.009236836323220412`) matching the untapered reference to `1.4e-13`, versus the old unconditional-taper value (`0.0092216090127`) it would previously have produced.

**Part D — refuse continuum construction on right-edge-singular potentials: fully fixed.** `tise_solver_main.cpp` now skips `buildContinuumState`/`matchAsymptotic`/`writeContinuumInfo` entirely when `sgr.rightEdgeSingular && continuumEnabled`, writing a `warnings.json` entry explaining the refusal instead of the old "treat with suspicion" text, and gating that warning itself on `continuumEnabled` (previously unconditional, which was noise for TISE-only runs). New tests confirm no `phase_shifts.dat`/`continuum_state_*.dat` are written and that the bound-state solve itself is unaffected (`E_1` still matches the exact Coulomb-function reference to `1e-9`).

**Part E — strengthened physics regression coverage: fully done** for every test class the plan named (`TestFiniteSquareWellRealSubprocess`, `TestHydrogenConfigFileRealSubprocess`, `TestCase3RemediationRealSubprocess`, `TestRightEdgeSingularWarningRealSubprocess`, `TestInteriorSingularityRealSubprocess`), each now asserting exact numeric values sourced from the reports (tightened finite-square-well phase-shift tolerance from `5e-2` to `5e-4`; added $d\delta/dE$ assertions to both continuum-enabled configs; added a hydrogen $\delta \bmod \pi$ regression against the report's reference table; added a regression pin confirming hydrogen's $d\delta/dE$ no longer diverges to +211). free_particle/harmonic_oscillator needed no changes, matching both reports' clean PASS verdicts.
