# TISE classifier configurability: what's worth exposing?

> Companion doc to `interface-implementation-cleanup.md`, same convention: planning only, no code changes here. Produced after Task 1 (`e5d54c9`..`446d241`) turned a set of previously-hardcoded magic numbers in `TISE/tise.hpp`/`TISE/tise.cpp` into named constants and, for most of them, optional C++ function parameters. This doc asks the next question: of those new parameters, which ones are worth threading further up the stack — as a `tise_solver` CLI flag, or a new `config.yaml` key — versus which should stay reachable only by C++ code that calls the library functions directly?

## Why this question has a concrete answer now

Before `8236239`, `tise_solver_main.cpp` was closer to a stub: it built a plain uniform grid, hardcoded the classic `{1}` B-spline drop-set, and had no path to strategic node placement or A4b singular-B-spline removal at all. Since then it is a real config-driven production pipeline: `tise_solver --config <config.yaml> --output-dir <dir>` (the only two CLI flags that exist today — see `TISE/tise_solver_main.cpp:34-79`) reads `config.yaml`, calls the same library functions this doc is about, and writes `eigenvalues.dat`/`eigenvectors.dat`/`phase_shifts.dat`/`continuum_state_NNN.dat`/`warnings.json`. The repo's `config.yaml` already has a `tise:` section with a `continuum:` sub-block (`n_energies`, `E_threshold`, `E_max`, `n_pts`), so "add a config key" is not a new pattern to invent — it's an existing convention to extend.

That said, several of Task 1's new parameters are, right now, *not reachable* even from `tise_solver_main.cpp`'s own direct calls into `tise.hpp` — the call sites that exist today pass only the required positional arguments and let every optional parameter fall back to its default. That fact matters as much as "is this parameter useful" when deciding what's worth exposing, and is called out per-row below.

## Parameter inventory

| Function | Parameter | Default | What it controls |
|---|---|---|---|
| `classifyAsymptote` | `numSamples` | `16` | How many geometrically-spaced sample points are used to probe the potential's tail toward `+-infinity`. |
| `classifyAsymptote` | `ratio` | `4.0` | The geometric growth factor between successive probe points (sample `k` sits at distance `reference + sign * scale * ratio^k`). |
| `classifyAsymptote` | `backupScale` | `1.0` | Floor on the first probe step's size, used when the domain boundary itself is at/near `x=0` (otherwise `|reference|` alone would give a zero-width first step). |
| `classifyAsymptote` | `coulombExponentTol` | `0.15` | How far the fitted power-law exponent may drift from exactly `1` and still be classified as a Coulomb (`~1/r`) tail rather than an unrecognized "Irregular" tail. |
| `classifyAsymptote` | `transitionWidthFraction` | `0.1` | For an Irregular tail, the recommended Case-3 taper width, as a fraction of the total domain span `(xMax - xMin)`. |
| `isSingularApproaching` (file-local to `tise.cpp`) | `numSamples`, `ratio`, `backupScale` | same three constants as `classifyAsymptote` | Same probing idea as above, but probing *inward* toward a finite interior join point instead of outward toward infinity. |
| `isSingularApproaching` (file-local to `tise.cpp`) | `pieceWidthClampFraction` | `0.25` | Caps the first probe step at this fraction of the potential piece's own width, so probing near a join can't overshoot into the neighboring piece (needed because, unlike `classifyAsymptote`, the probe here is bounded on both sides, not free to grow outward). |
| `classifySequenceConvergence` | `flatnessAbsTol` | `1e-10` | Absolute part of the "is this sequence already flat" tolerance: if the largest successive difference is below `flatnessAbsTol + flatnessRelTol * maxAbsV`, the sequence is declared flat/converged rather than divergent or power-law. |
| `classifySequenceConvergence` | `flatnessRelTol` | `1e-9` | Relative part of the same flatness tolerance, scaled by the sequence's own largest magnitude — keeps the flatness check meaningful for potentials that are large in magnitude but still flat. |
| `classifySequenceConvergence` | `shrinkFactorFloor` | `1e-300` | Denominator floor in the divergence check (ratio of the last successive difference to the mid-window one), guarding against division by a near-zero difference. |
| `classifySequenceConvergence` | `divergenceThreshold` | `0.5` | If the end-of-window/mid-window difference ratio hasn't shrunk below this threshold, the sequence is classified divergent (blowing up, e.g. approaching a `1/x` pole) instead of settling to a finite limit. |
| `classifySequenceConvergence` | `windowSize` | `7` | The tail window used for the power-law-exponent fit starts `windowSize` samples back from the end of `V`; the fit itself uses `windowSize - 2` successive-difference-ratio estimates from that window (median of those log-ratio estimates), not `windowSize` differences directly. Both `V.size()` and `windowSize` must be `>= 3` (validated; throws otherwise), or there would be no estimate to take the median of. |
| `detectPotentialStructure` | `valueJumpTol` | `1e-6` | How large a one-sided-estimated jump in `V(x0)` itself must be, at a piece-to-piece join, to classify that join as a `Step` (discontinuous potential). |
| `detectPotentialStructure` | `slopeJumpTol` | `1e-4` | Same idea for `V'(x0)`: a slope mismatch bigger than this (with no value jump) classifies the join as a `StitchedKink`. |
| `detectPotentialStructure` | `fdStep` | `1e-4` | Base step size for the one-sided finite-difference value/slope estimates used at each join. |
| `detectPotentialStructure` | `stepClampFraction` | `0.1` | Caps the finite-difference step at this fraction of a piece's own width, so probing near a join can't step outside a narrow piece into its neighbor. |
| `buildStrategicGridAndDropSet` | `edgeTolerance` | `1e-9` | How close a detected `Singular` join's location must be to `rMin`/`rMax` to be treated as "already regularized by the domain wall" rather than a genuine interior singularity needing its own B-spline removal. |
| `solveTISE` | `continuumOutputPoints` | `301` | Number of spatial sample points written per `continuum_state_NNN.dat` block. |

Two functions Task 1 also touched are intentionally **absent** from this table because the brief's own disposition for them was "name the constant, do not add a parameter": `computeEAcc`'s `2.0` physics-formula coefficient, and `validateNoOverlappingPotentialPieces`'s `kUnboundedProbeMagnitude`. Neither is a tunable knob in the same sense as the rows above, so there's nothing here to recommend exposing.

## Recommendations

### Stays API-only: `isSingularApproaching`'s params, `classifySequenceConvergence`'s params

These two groups share a structural reason to stay internal, not just a "not useful enough" judgment call:

- **`isSingularApproaching` is not part of the public API at all.** It lives in an anonymous (file-local) namespace inside `tise.cpp` — no code outside that translation unit can call it, full stop. Its only caller, `detectPotentialStructure`, invokes it as `isSingularApproaching(potential, x0, sign, width)` — four positional arguments, every optional parameter (`numSamples`, `ratio`, `backupScale`, `pieceWidthClampFraction`) left at its default (`TISE/tise.cpp:1017-1018, 1057, 1064`). `detectPotentialStructure`'s own signature has no corresponding parameters to forward them through. So exposing any of these via CLI/config would first require a separate, non-trivial code change — extending `detectPotentialStructure`'s own parameter list and threading four more values through it — before there's anything for a config key to even target. That's a bigger step than "expose an existing knob," and nothing in the current requirements asks for per-join probing control at that granularity.
- **`classifySequenceConvergence` is public, but its five tuning parameters are currently unreachable from either of its two real callers.** `classifyAsymptote` calls it as `classifySequenceConvergence(V, ratio)` (`TISE/tise.cpp:361`) — only `V` and `ratio`, nothing else — and `isSingularApproaching` does the same (`TISE/tise.cpp:945`). Both callers let `flatnessAbsTol`/`flatnessRelTol`/`shrinkFactorFloor`/`divergenceThreshold`/`windowSize` fall back to their compiled-in defaults. So, exactly like the previous group, exposing any of these five would first mean adding matching pass-through parameters to `classifyAsymptote` (a public, driver-reachable function) — a real API change, not just a config/CLI wiring change.
- Numerically, these are also the hardest parameters to justify exposing to a `config.yaml` author: they tune curve-fitting robustness (how many points to use, how to detect "already flat" vs. "diverging" vs. "power law"), not physics. A wrong value doesn't change what problem is being solved; it risks misclassifying a join/asymptote silently. That argues for keeping them as call-site literals a C++ maintainer sets deliberately, with test coverage backing the choice, rather than something an end user tunes per run without full visibility into the numerical-fitting algorithm they're perturbing.

**Recommendation: leave all of these API-only.** If a future need arises (e.g., a potential whose tail genuinely needs `numSamples` above 16 to resolve), the right first step is plumbing them through the nearest public function's own parameter list (as Task 1 already did one level up) — a small, separate follow-up — not jumping straight to a config key for a knob nothing currently forwards to.

### Stays API-only (for now), narrower reason: `detectPotentialStructure`'s four parameters

`detectPotentialStructure` is public and its four parameters (`valueJumpTol`, `slopeJumpTol`, `fdStep`, `stepClampFraction`) are real, well-documented physics/numerics knobs (how big a jump in V or V' counts as structure). But its only production caller, `buildStrategicGridAndDropSet`, invokes it as `detectPotentialStructure(potential)` (`TISE/tise.cpp:1248`) — no overrides, same one-level-of-plumbing gap as the previous section. Unlike the `classifySequenceConvergence`/`isSingularApproaching` group, though, these four thresholds are comparatively easy for a `config.yaml` author to reason about ("how big a discontinuity counts as a Step") if the plumbing gap were closed. **Recommendation: API-only today, but flag as the best candidate for a *future* two-step promotion** (first thread through `buildStrategicGridAndDropSet`, then decide on config exposure) if a real config ever needs a potential whose joins are subtler than the current defaults can classify correctly — nothing in the current test suite or `config.yaml` surfaces that need yet.

### Worth exposing: `buildStrategicGridAndDropSet`'s `edgeTolerance`

Unlike every parameter above, `edgeTolerance` is reachable today at both of `buildStrategicGridAndDropSet`'s real call sites without any further plumbing: `solveTISE` (`TISE/tise.cpp:1316`) and `tise_solver_main.cpp` (`TISE/tise_solver_main.cpp:200`) both call `buildStrategicGridAndDropSet` **directly**, and both currently omit the argument (using the default). This is the one parameter in this table where "add a config key and pass it through" is a single, direct hop — no intermediate function needs a new parameter first.

It's also physically meaningful to a `config.yaml` author in a way that's easy to explain: it answers "how close does a singular point have to be to my box wall before I treat it as already handled by the wall, instead of needing its own extra B-spline removal?" The default (`1e-9`) is deliberately far below any physically meaningful distance and far above float round-off, so in practice this only matters for an edge-case config where a singularity is placed *deliberately* very close to (but not exactly at) `rMin`/`rMax` and the author wants to control which regularization path handles it.

**Recommendation: worth exposing, low priority.** It's a legitimate knob and cheap to wire, but the current `config.yaml`/test suite has no potential that exercises the "near-edge, not exactly-at-edge" case this tolerance actually discriminates — so there's no concrete failing scenario motivating it today. Good candidate for the next time someone adds a config with a near-boundary singularity and needs to reason about which side of this tolerance it falls on.

### Worth exposing, but already effectively available: `classifyAsymptote`'s five parameters

`tise_solver_main.cpp` calls `classifyAsymptote` directly (`TISE/tise_solver_main.cpp:281-282`), passing only `potential`, `domain`, `side`, and `warnOut` — every one of `numSamples`/`ratio`/`backupScale`/`coulombExponentTol`/`transitionWidthFraction` falls back to its default. Like `edgeTolerance`, this is a single-hop exposure (no intermediate function needs new plumbing).

Two of the five (`coulombExponentTol`, `transitionWidthFraction`) are genuinely interesting to a config author: they control, respectively, "how strict is the Coulomb-tail check" and "how wide should the Case-3 taper be." The other three (`numSamples`, `ratio`, `backupScale`) are numerical-sampling knobs in the same spirit as the API-only group above — useful for a C++ developer debugging a misclassification, less so for a `config.yaml` author who doesn't know what a geometric probe sequence is.

**Recommendation: worth exposing `coulombExponentTol` and `transitionWidthFraction` specifically; leave `numSamples`/`ratio`/`backupScale` API-only** (reachable via direct `tise::classifyAsymptote(...)` calls in C++, e.g. from a test or a future driver, but not worth a config key). Medium priority — Case-3 (Irregular-tail) handling is a real, if uncommon, path in the current pipeline (`tise_solver_main.cpp`'s own Case-3 block, `TISE/tise_solver_main.cpp:246-304`), so a user who hits it and wants to widen or narrow the taper has a legitimate reason to want this without recompiling.

### Not applicable to `tise_solver` today: `solveTISE`'s `continuumOutputPoints`

This one is worth spelling out because the obvious-looking answer ("of course, expose the continuum output resolution") turns out to be moot for the CLI this doc is scoped to. `tise_solver_main.cpp` does **not** call `solveTISE` at all — it re-implements the same pipeline steps inline (`buildStrategicGridAndDropSet`, `fillBandedMatrices`, `solveGeneralizedEigenproblem`, `buildContinuumState`, `matchAsymptotic`, `writeContinuumInfo`, directly). Its equivalent knob is `writeContinuumInfo`'s own `npts` argument, which is already wired straight from `config.yaml`'s existing `tise.continuum.n_pts` key (`TISE/tise_solver_main.cpp:229, 393-394`) — with no dependency on `solveTISE` or its `continuumOutputPoints` parameter whatsoever.

`solveTISE`'s `continuumOutputPoints` parameter is consumed only by `main.cpp` (the `H-BoundStates` demo driver, `TISE/main.cpp:84`), which itself has no CLI or config surface at all — it's a hardcoded-constants demo binary, not a config-driven pipeline. **Recommendation: no exposure work needed for `tise_solver`** (its functional equivalent, `n_pts`, already exists in `config.yaml`). If `H-BoundStates`/`main.cpp` ever grows its own CLI or config file, `continuumOutputPoints` would be the natural knob to expose there — but that's a speculative future scope, not this doc's job to plan.

## Mechanical path for the exposure-worthy candidates

Two candidates were recommended above: `buildStrategicGridAndDropSet`'s `edgeTolerance`, and `classifyAsymptote`'s `coulombExponentTol`/`transitionWidthFraction`. For each, here's what would actually need to change (described only — not implemented in this task):

**`edgeTolerance`:**
1. `config.yaml` schema: add a new key, e.g. `bspline.edge_tolerance` (optional, default `1e-9` if absent — matching `kDefaultEdgeTolerance` so an omitted key changes nothing).
2. `tise_solver_main.cpp`: read it near the other `bspline.*` reads (`TISE/tise_solver_main.cpp:173-176`), guarding for the key's absence the same way `n_pts_eigenstate`/`continuum.*` already do; pass it as `buildStrategicGridAndDropSet`'s sixth argument at its existing call site (`:200`).
3. No CLI flag needed — this is a per-run physics/numerics setting, which is exactly what `config.yaml` (not `--config`/`--output-dir`, the only CLI-level concerns) is for in this pipeline's existing design.
4. Docs: `TISE/README.md`'s config-schema section (once it documents the real pipeline per Task 3's scope) and the inline `config.yaml` comment block (`config.yaml:17-21`'s `bspline:` section) would both need the new key's meaning and default noted, in the same one-line comment style already used there (e.g. `n_pts_eigenstate: 301  # spatial grid points for eigenstate output`).

**`coulombExponentTol` / `transitionWidthFraction`:**
1. `config.yaml` schema: both are Case-3/asymptote-classification settings, so a natural home is a new small block, e.g. under `tise:` — `tise.asymptote_classification.coulomb_exponent_tol` and `tise.asymptote_classification.transition_width_fraction` — rather than reusing the existing `tise.continuum` block, since asymptote classification runs regardless of whether `continuum.enabled` is true.
2. `tise_solver_main.cpp`: read both (optional, defaulting to `kDefault...`-style constants mirrored from `tise.hpp` if the block/keys are absent) before the Case-3 block (`TISE/tise_solver_main.cpp:246-304`); pass them as `classifyAsymptote`'s 8th/9th arguments at its call site (`:281-282`), which currently stops after `warnOut`.
3. No CLI flag needed, for the same reason as `edgeTolerance` — this is per-run physics tuning, not a pipeline-invocation concern.
4. Docs: `TISE/README.md` and the `config.yaml` comment block would need the two new keys explained in physics terms accessible to a config author (e.g. "how close to a pure `1/r` tail counts as Coulomb," "how wide the smoothing taper is, as a fraction of the box size") — not in terms of the underlying power-law-fit implementation.

In all cases, the mechanical shape is the same: a new optional `config.yaml` key with a default matching the existing C++ default (so an omitted key is provably a no-op), one or two lines added at an existing `tise_solver_main.cpp` read site, one argument threaded to an already-direct call site, and a doc/comment update. None of these need a new CLI flag under the current design, since `tise_solver`'s CLI surface is deliberately minimal (`--config`, `--output-dir` only) and everything run-specific already lives in `config.yaml`.

## Note: the "probe far from a boundary" idiom appears three times, independently

While reading through the call sites above, the same underlying idea — "evaluate the potential at a point so far away it stands in for infinity" — turns up three separate times in the codebase, each with its own independently-named constant and its own scale:

1. `classifyAsymptote`'s own `scale` (`TISE/tise.cpp:355`): `std::max(std::abs(reference), backupScale)`, then sampled at `reference + sign * scale * ratio^k` for `k` up to `numSamples-1` — geometric growth, reaching roughly `scale * ratio^15` at the far end with the current defaults.
2. `tise_solver_main.cpp`'s local `probeX` (`TISE/tise_solver_main.cpp:256-265`): `rMax + kProbeDistanceMultiplier * std::max(std::abs(rMax), kProbeDistanceFloor)`, with `kProbeDistanceMultiplier = 1.0e6` — a single very-far point, not a geometric sequence.
3. `validateNoOverlappingPotentialPieces`'s local `kUnboundedProbeMagnitude` (`TISE/tise.cpp:165-171`): `std::numeric_limits<double>::max()/4.0` — a magnitude close to the largest representable `double`, used to probe an unbounded piece's own domain-overlap check.

Task 1's own self-review (see `task-1-report.md`) explicitly considered and rejected unifying these under one shared constant, on the grounds that each solves a genuinely distinct problem: (1) needs a *sequence* of points for curve-fitting, not just one; (2) needs one point far enough to be "certainly still inside an unbounded piece" without overflowing `evaluateFunction`'s underlying `muparser` evaluation; (3) needs a magnitude near numeric limits specifically to stress-test domain-overlap logic, not to evaluate a potential expression (which could legitimately overflow at that scale). That reasoning holds up: none of the three is a drop-in substitute for either other one, and forcing them to share a constant would create a coupling between three unrelated call sites that happens to type-check but isn't physically meaningful.

This is flagged here, per this task's brief, as a **candidate for a future simplification pass, not undertaken now**: if a future maintainer ever needs to change how "far away" means for one of these, the fact that there are three independent places encoding a similar idea is worth knowing about, even though each is individually justified. A worthwhile future exercise (out of scope here) would be to write a short shared doc comment cross-referencing all three (each already partially does this — `TISE/tise_solver_main.cpp:248-255` explicitly points at the other two) so a reader who finds one is pointed at the others, without actually merging the implementations.
